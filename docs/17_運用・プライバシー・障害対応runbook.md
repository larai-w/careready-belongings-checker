# CareReady 運用・プライバシー・障害対応 Runbook(Issue #11)

最終更新: 2026-08-01

## 目的と公開境界

クローズドパイロットを、創業者個人の記憶や非公開の会話だけに依存せず運用するための基準を定める。公開リポジトリには、個人の電話番号・メールアドレス、施設名、参加者情報、認証情報、共有コード、ケアデータ、内部インシデント原文を保存しない。

実際の担当者連絡先、パイロット参加者への連絡網、認証情報、未公開のインシデント記録は、公開リポジトリ外の管理領域で保持する。公開Issueには、件数・重大度・状態・再発防止など、機微情報を除いた要約だけを残す。

## 問い合わせ経路と担当ロール

| 対象 | 公開の受付経路 | 一次担当ロール | 利用条件 |
|---|---|---|---|
| 家族利用者 | アプリ内「困ったこと・ご意見を送る」 / veai公式LINE | Support owner | 氏名、病歴、施設名、共有コードを送らないよう案内する |
| 施設スタッフ | パイロット時に別途案内する担当窓口 / veai公式LINE | Facility liaison | アカウント復旧は認証runbookに従い、パスワードをメッセージで受け取らない |
| セキュリティ報告 | GitHub Private Security Advisory | Technical responder / Privacy owner | 公開Issueを使わず、ケアデータの添付を避ける |
| 緊急の体調・事故 | 施設、医療機関、地域の緊急窓口 | CareReadyの対象外 | CareReadyは医療判断・緊急対応の代替ではない |

Support ownerは受付と重大度判定、Facility liaisonは施設への非技術説明、Technical responderは封じ込めと復旧、Privacy ownerはデータ露出時の停止判断を担当する。少人数運用で同一人物が複数ロールを兼ねる場合も、判断したロールを非公開ログに明記する。

## データ取扱いの運用事実

利用者向け説明は [`privacy.html`](../privacy.html) を正とする。実装変更時は、同ページとこの表を同時に更新する。

| データ | 保存先 / 送信先 | 削除・保持の扱い |
|---|---|---|
| チェック、メモ、呼び名、日記、写真、条件、取込済み施設テンプレ | 利用者端末のIndexedDB | アプリの全削除で端末から削除。サーバー側の施設原本には影響しない |
| 施設テンプレ、施設名・電話・住所、共有コード | DynamoDB。施設アカウント単位でスコープ | 施設管理画面でテンプレを削除するとコードも無効。パイロット終了時に不要テンプレがないことをFacility liaisonが確認 |
| URL / LINE共有データ | URL内。受信者の端末に取込可能 | URLを知る相手が読めるため、公開投稿しない。サーバーで共有URLを失効させる仕組みはない |
| OCR画像 | CareReady APIから設定済みOCRプロバイダーへ一時送信 | CareReadyのDynamoDB/S3には元画像を保存しない。識別情報が写る画像を使わせない |
| フィードバック本文、任意連絡先、接続元IP | DynamoDB、SNS通知 | 返信先は対応完了後30日以内、本文と接続元IPは90日以内を目安に手動削除。継続中のセキュリティ調査は理由と期限を非公開ログに記録 |
| Web Push購読情報 | DynamoDB | オンラインで通知OFF時に削除。無効な通知先は送信時の404/410でも削除。予定日は端末内のみ |

## 重大度と停止基準

### SEV-0: 即時停止

次のいずれかが疑われる場合は、新規パイロット利用を直ちに止め、Privacy ownerとTechnical responderへ同時に連絡する。

- 認証回避、別施設テンプレートの閲覧、共有コードの大量露出
- 認証情報、個人情報、健康情報、施設特定情報の公開または第三者送信
- 利用者データの広範な消失・改変
- CareReadyが緊急対応や医療判断を代替すると誤認させる挙動

### SEV-1: 次回利用前に修正

- 主要フロー(施設サインイン、テンプレ作成、取込、オフライン再表示)が完走できない
- 印刷・帰宅確認・条件切替の重大な表示崩れや状態不整合
- 通知、OCR、フィードバックの継続的な失敗や濫用

新規招待を止め、既存利用者へ影響範囲と代替手順だけを案内する。個人・施設を特定する原因説明は公開しない。

### SEV-2: 通常対応

主要フローを妨げない文言、軽微な表示、改善要望。Issueへ公開可能な再現条件と受け入れ条件を記録し、通常の優先順位付けを行う。

## 初動手順

1. 受付時刻、報告経路、重大度、影響する機能だけを非公開インシデント記録へ残す。ケアデータの複製を避ける。
2. SEV-0/1は新規パイロット招待と新規コード配布を止める。
3. 影響範囲を「家族端末 / 施設管理 / 公開API / 通知・OCR・フィードバック / デプロイ」に分ける。
4. 最小の封じ込めを実行し、データを削除する前に必要な非機密メタデータ(時刻、HTTP状態、commit、Actions run)を保存する。
5. 復旧後に本番スモークと実機ゲートを再実施する。公開Issueは事実を匿名化できる場合だけ更新する。

## サービス封じ込め

| 影響 | 最初の封じ込め | 注意点 |
|---|---|---|
| 施設アカウント侵害 | 対象Cognitoユーザーを無効化し、認証runbookで復旧 | `custom:facilityId`未設定時は`sub`がスコープになるため、安易なユーザー再作成で既存テンプレを孤立させない |
| 共有コード露出 | 対象テンプレートを施設管理画面で削除 | コード単体の失効機能はない。削除前に施設へ影響を確認する |
| 公開API濫用 | API Gateway/Lambda側で対象ルートの制限・停止を検討 | フロントのボタン非表示だけではAPIを封じ込められない。CDK変更は人間承認後にデプロイする |
| フロント表示障害 | 新規案内を止め、既知の正常版へロールバック | 家族端末のローカルデータを削除させない。オフライン利用への影響を確認する |
| フィードバック通知障害 | DynamoDB保存の有無とSNS通知を分けて確認 | 通知失敗でもAPIは成功する設計。通知だけで受付件数を判断しない |

## フロントエンドのロールバック

1. `main`の問題commitと、直前の正常なDeploy run・commitを特定する。
2. 現在の`main`から修正ブランチを作り、`git revert`で問題commitを打ち消す。履歴の強制書換えや`git reset --hard`は使わない。
3. Service Worker配信物を戻す場合も、`CACHE_NAME`は過去値へ戻さず新しい連番へ進める。既存端末が古いキャッシュを再利用するのを防ぐ。
4. 公開境界検査、構文、データ、バックエンド、ヘッドレススモーク/E2Eを実行し、PRで差分を確認する。
5. `main`へマージし、DeployとCloudFront invalidationの成功を確認する。
6. 本番の家族画面、施設サインイン、既存コード取込、オフライン再表示を確認してから新規案内を再開する。

## バックエンドの復旧

1. DynamoDBとCognitoは`RETAIN`対象であり、削除・再作成を復旧手段にしない。
2. リポジトリの既知正常commit、CloudFormation、Lambda設定の対応を確認する。
3. 既知正常commitから`cdk synth`と`cdk diff`を確認する。実デプロイはGitHub Actionsの手動workflowとproduction環境承認を使う。
4. 施設CRUD、公開redeemの404/成功、認証なしAPIの拒否、フィードバック保存と通知を非機密データで確認する。
5. 復旧結果、未解決リスク、再開判断者のロールを非公開ログへ記録する。

## 公開可能な完了記録

IssueやProjectへは次だけを記録できる。

- 発生日と解消日
- 重大度と影響した機能
- critical/major/minorの件数
- 修正PR、commit、CI/Deploy run
- 個人・施設を特定しない再発防止策

認証値、メール、共有コード、IP、入力本文、画像、施設名、参加者情報は記録しない。
