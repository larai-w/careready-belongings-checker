# CareReady 開発戦略

## 1. プロダクトの定義

**CareReady = 介護の外出・移動に伴う「持ち物準備」を、家族と施設の間で確実にするツール**

介護における持ち物準備は:
- 行き先(ショートステイ / 入院 / デイサービス / 施設入所)ごとに必要物が違う
- 「名前の記入」「おむつの枚数」など施設固有ルールがある
- 準備するのは本人ではなく**家族**、確認するのは**施設スタッフ**
- 忘れ物が発生すると、家族が施設まで届け直すコストが大きい

この「家族⇄施設の非対称な共同作業」を解決するのが本質的価値。単なるTODOアプリとの違いはここにある。

## 2. 現行ロードマップ（2026-07-15更新）

### V0: 本番安全化・クローズドパイロット

- パイロットアカウントのパスワード変更
- 管理画面から家族向けPWAまでの実機E2E
- パイロット施設で持ち物34項目、配布フロー、価格仮説を検証
- 実機と現場で見つかった不具合のみを先に修正

### V1: SEOコンテンツの基盤作り

- 現場確認後に「ショートステイ 持ち物」などの情報記事を公開
- クローズドパイロット中は本番PWAへの強いCTAを置かず、プロジェクト紹介または開発中表示に留める
- Search Console の表示クエリとCTRを見て、検索者が求める情報を学ぶ

### V2: 証拠による機能選択

- 家族の端末間同期・分担需要が強い → B-4（LINEログイン+同期）
- 施設の準備進捗需要が強い → B-5（施設ダッシュボード）
- 施設指定の数量・名称・注記需要が強い → 施設オーバーライド拡張
- 身近な家族の反復利用、重大不具なし、持ち物内容の確認、問い合わせ対応方法が揃った時点で、一般向け導線を別途判断する

### V3: 同じ「ケアの移動」へ水平展開

ショートステイ → デイサービス・通所リハ → 体験入所・施設入所 → 高齢者の入院・転院の順に、テンプレートとSEOクラスターを広げる。旅行・子育て・災害持出への汎用化は、介護特化の強みを薄めるため当面行わない。

## 3. 初期ロードマップ（履歴）

### Phase 0: 足場固め(2〜4週間)
**ゴール: 今のプロトタイプを「壊れない・消えない」状態にする**

- [ ] API_URL の確定とバックエンド疎通(現在プレースホルダのまま)
- [ ] XSS対策・エラーハンドリング強化
- [ ] PWA化(オフラインで開ける・ホーム画面に追加できる)
- [ ] localStorage → IndexedDB 移行(データ消失リスク低減)
- [ ] Git管理開始・デプロイパイプライン構築 ※現在リポジトリ未初期化
- [ ] 実ユーザー(身近な介護家族)1〜3名でのドッグフーディング

### Phase 1: MVP(1.5〜2ヶ月)
**ゴール: 「共有できる」「テンプレートから作れる」**

- [ ] フレームワーク移行(Svelte/React + TypeScript)
- [ ] アカウント(LINEログイン)
- [ ] リストのURL共有(家族→もう一人の家族、家族→施設)
- [ ] テンプレート機能(「ショートステイ2泊3日」等の雛形から自分用リスト作成)
- [ ] アイテムの追加・編集・削除(現状はAPI供給の固定リストのみ)
- [ ] 数量指定(「おむつ ×20」)と名前記入チェック

**MVP判定基準: 「次のショートステイでもまた使いたい」と言うユーザーが5人いること**

### Phase 2: 差別化(2〜3ヶ月)
**ゴール: 「CareReadyでないとダメ」な理由を作る**

- [ ] AI持ち物リスト生成(Claude API): 要介護度・日数・季節・施設種別からリスト草案を自動生成
- [ ] 施設側アカウント: 施設が公式テンプレートを配布 → 家族がワンタップ取込
- [ ] 帰宅時チェック(持って行った物が全部戻ったかの逆方向チェック)← 介護あるあるの紛失問題に効く
- [ ] プッシュ通知(前日リマインド)
- [ ] PDF/印刷出力

### Phase 3: 事業化(3ヶ月〜)
- [ ] 施設向け管理画面(B2B)
- [ ] veai エコシステム他サービスとの連携
- [ ] 入院・災害持出袋など隣接ユースケースへの水平展開

## 4. 開発の進め方

| 方針 | 内容 |
|---|---|
| リリース単位 | 2週間スプリント。毎スプリント末に本番反映 |
| 品質 | チェック状態の永続化はE2Eテスト必須(データ消失=即アンインストール級の致命傷) |
| 計測 | 最初から「リスト作成数」「再訪率」「共有実行率」の3指標だけ計測 |
| 技術的負債 | Phase 0 のうちに Vanilla JS のまま直せる物は直し、Phase 1 で一括移行(中途半端な併存はしない) |
| AI活用 | 実装の大部分は Claude Code で高速化。人間は仕様判断・ユーザーテスト・施設折衝に集中 |

## 5. リスクと対策

| リスク | 対策 |
|---|---|
| ターゲット層(50〜70代)にダークUIが刺さらない | Phase 0 でライトテーマ切替を用意しABテスト |
| 施設側の協力が得られない | まず家族単独で完結する価値(共有・テンプレ)を先に固める |
| 類似アプリ(汎用パッキングアプリ)との競合 | 「施設ルール対応」「帰宅時逆チェック」「AI生成」の介護特化3点で差別化 |
| 開発リソース不足 | Phase 1 までは1人+AIで完遂できるスコープに厳守 |
